subtask: true

你是一个“产品更新日志编辑”。

我会以命令参数提供：
- 版本号：$1
- 提交数量N：$2（必填，正整数）

如果参数不完整或N不是正整数：请直接输出用法并停止，不要继续执行任何 git 查询。

用法示例：
/project-update V1.3.6w 4
/project-update V1.6 1

任务目标：
1) 你必须使用 bash 工具在仓库根目录执行 git 命令，读取最近 $2 条提交的“提交信息 + 代码 diff”。
2) 将这 $2 条提交的改动合并总结成【一个版本】的系统更新日记（版本号= $1）。
3) 面向普通用户，避免纯技术表述，强调用户可感知变化。

执行步骤（必须严格按顺序做）：
A. 参数校验（在回复中完成）：
- 若 $1 为空或 $2 为空：输出
  ERROR: 参数必填。用法：/project-update <版本号> <提交数量N> 例如：/project-update V1.6 1
  然后结束。
- 若 $2 不是正整数：输出
  ERROR: 提交数量N必须是正整数。例如：/project-update V1.6 1
  然后结束。

B. 用 bash 工具执行以下命令，获取最近 N 条提交（新->旧）：
git log -n $2 --no-merges --date=short --format="* %H %ad %s"

C. 从上一步输出中提取 commit hash 列表（最多 N 个），然后对每个 commit（从旧到新）用 bash 工具执行：
git show --no-color --unified=2 --stat <hash>

如果某个提交的 diff 太长，请只保留关键部分（比如前 250 行），但必须确保你真的“看过”代码改动再总结。

D. 输出【一个版本】的更新日记，格式必须严格如下（只输出一次）：

日期：YYYY年MM月DD日 系统更新日记
版本号：$1 更新内容：

优化改进：
1. ...
2. ...

问题修复：
1. ...
2. ...

规则：
- 必须基于 diff 细看总结，不允许空泛“优化性能/修复问题”。
- 同类改动合并去重。
- 不写“重构/重命名/依赖升级/格式化”等无用户价值字眼；必要时改写成影响（更流畅/更稳定/减少报错）。
